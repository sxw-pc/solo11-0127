# 面单印发核台

物流站点把本地面单软件的打印作业、主管重印授权和承运回执采入同一 SQLite 证据账。印制判断纸号、模板与回执；重印裁决原份作废和新份生效；交接核对面单、重量、承运人，并独立结算整批交接。原始桌面导出字节及 SHA-256 持久化，JSON 报告列来源、实体、问题和每次业务决定。

四个入口分别是 `print-import`、`reprint-request`、`handoff-evaluate` 和 `handoff-settle`，均接收 `--db ledger.db export.json`。导出 JSON 顶层含 `version` 和 `rows`。`demo` 会在临时目录生成完整正常链路；测试还覆盖纸号冲突、缺打印回执、授权过期、重量不符及部分失败结算。

打印资源是独立的排程决定：`printer-plan` 读取桌面设备与纸库存快照，为份次分配支持模板且有纸、有空闲容量的打印机。`printer-cancel` 必须提供无纸张输出的操作员证据才释放预留；已消耗的纸张不会因重试回到库存。印制及授权补印会读取排程结果，资源不足时等待。

承运方接收后仍可提出实物争议：`carrier-claim` 核对实际看到的面单份次，证实不符时把包裹置于召回中、把已结算批次重开；`recall-resolve` 依实物扫描证据结束追索。争议被驳回时原交接结论不变，重放旧结算导出也不能重新封账。无有效原份、占用中的新份 ID 或已用纸号不能获批重印；召回中的包裹不能再次交接。相关来源、预留、索赔与召回实体均写入台账；演示只用本地虚构文件。

承运商月底离线账单（`bill-import`，整数分金额）只含结算批次、收件日、服务档位、计费区间和金额，部分行有包裹号或承运商后补行号。系统只用这些真实可用字段在账单行与合格交接（含已争议交接）之间建立一对一候选关系，回溯枚举覆盖全部账单行的完整可行匹配，绝不让同一交接在一个匹配中承担两笔正向收费；无完整匹配、缺字段、非正整数金额、重复行号及同身份异文一律保留待核或记为冲突。核对结果给出每个批次的全部可行匹配、精确归属行以及无争议可付金额的上下界：`bill-pay --policy strict` 只为在所有可行匹配中归属一致的行付款（归属不明即付 0），`--policy lower_bound` 按整批担保下界先付任何可行归属下都不低于的无争议金额，但不会把某一行谎称已归属某一交接。实际付款生成不可改写的付款凭证，重复指令不会二次付款。

争议在付款后成立时，原账单、历史付款决定与凭证全部保留，系统按争议后的交接状态重新核对并产生新决定：争议件收费移出可付部分，已实付而不再可付的差额另记追收余额（`clawback`），实物交接历史不变；未付款前发生争议只更新核对区间，不虚构凭证或追收。承运商随后通过 `bill-reference` 提交带来源摘要（SHA-256）的行号对照表：摘要必须对应已留存的账单导出，对照表只缩小候选关系，绝不静默覆盖原账单；摘要不符、指向缺失行、与真实字段不兼容或同行号异文均待核/冲突处理，不会被当成事实。报告（`report`）在 `billing` 段列每笔账单的可行匹配、金额上下界、已付与追收余额。

运行：`python -m pip install . --no-deps --no-build-isolation`，`python -m labeldispatch demo`，`python -m labeldispatch --help`，`python -m pytest -q`。所有演示和测试使用虚构本地文件，不访问网络。
